# 映溯 CineTrace · 单视频上传与 Video Context

**产品需求草案 v0.1 · 2026-11-19**

面向需要反复在长片中找素材的创作者。以一部两小时电影为例，用户可能先想知道「这段在讲什么」，再追问「哪句台词提到了钥匙」「谁真的把钥匙收了起来」。首版先把这三类问题需要的证据放到同一条可播放的时间线上。产品负责人依据样片实测决定下一版的查询体验。

用户一次选择一份视频，上传后可以离开再回来，查看按原片时间排列的语音、字幕和画面动作，从任意一条记录跳回原片。V1 的交付终点是可查看、可复用的 Video Context。自然语言提问用来检验数据是否足以支持后续检索；用户问答、回看核验循环、多 Agent 和剪辑留到下一轮产品设计。

## 用户如何完成一次任务

1. 在上传页选择一份视频，看到文件名、大小和处理说明，包括画面片段会发送到百炼进行视觉分析。首批验收素材使用浏览器可播放的 H.264 MP4，覆盖有声和无声视频。上传中断后重新选择同一文件，客户端查询已接收分片并补传缺片。
2. 系统验证文件完整性和视频流，保存原片，自动安排处理。页面分别显示「上传完成」「等待处理」和当前处理阶段。刷新页面或重启服务后仍能找回该任务。
3. 处理详情显示语音、字幕、动作各自的状态，以及生成检索块和摘要的进度。单轨失败时，用户能看到已完成的内容，并重试失败部分。
4. 结果页提供原片播放器、场景目录和三轨时间线。点场景能展开相关检索块，点证据能从该证据的起点播放。一次上传生成一个独立任务，历史任务可以重新打开。

## 视频中的三种信息

所有证据使用同一份原片的毫秒时间轴，区间采用左闭右开。单条证据记录来源、原文或观察描述、起止时间、媒体引用和提取方式。来源始终保留，例如屏幕上显示的字幕与实际说出的台词可能不同。

| 信息轨 | 首版工具与处理方式 | 证据示例 |
|---|---|---|
| 语音 | FFmpeg 取音轨，本地 faster-whisper 加载 Whisper 多语种 `turbo`，返回语段时间戳。音轨缺失或人声检测为空时，记录「无语音」。[转写与时间戳](https://github.com/SYSTRAN/faster-whisper#usage) | 12.1–14.4 秒，说话人说“钥匙给你”。 |
| 字幕 | 优先解析内封文本字幕轨，保留原始台词、语言和时间码。只有烧录字幕或图像字幕时，分别从画面字幕区域或解码后的字幕图像 OCR，起测采用 PaddleOCR 的 `PP-OCRv5_mobile_det` 与 `PP-OCRv5_mobile_rec`。合并连续重复文字并保留代表帧；OCR 边界标为采样估计。[OCR 模型文档](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html) | 12.0–14.8 秒，字幕显示“把钥匙收好”，来源为内封字幕。 |
| 动作 | Python 调用阿里云百炼 `qwen3-vl-plus`，输入有顺序的短视频画面，返回可见主体、动作、物体及片内时间。程序换算到原片时间，检查范围并记录对应片段。遮挡时只记录看得见的过程。无声、无字幕也要处理此轨。[模型说明](https://help.aliyun.com/zh/model-studio/qwen3-vl-plus) · [视频输入方式](https://help.aliyun.com/zh/model-studio/vision) | 14.1–16.2 秒，穿灰衣的人把钥匙放到桌面后松手。 |

「无内容」表示该轨已经检查完毕；「提取失败」表示结果尚不可靠。画面动作是模型对原片的观察，最终可核查的证据是对应的原片区间；代表帧方便预览动作发生的位置。V1 字幕识别关注影片字幕；场景中的招牌、包装文字单独标明来源，避免混入人物台词。

## 三层 Video Context

三层是同一时间轴的三种阅读粒度。每个检索块和场景都能分别列出语音、字幕与动作，也能展开到各自的原始证据。

| 层级 | 生成与保存规则 | 用户可以做什么 |
|---|---|---|
| L1 原始证据 | 保存原始语段、字幕条目、视觉观察及其原片定位。每条有稳定的 evidence_id。换算后满足 0 ≤ 开始 < 结束 ≤ 视频时长。 | 区分“听到了什么”“字幕写了什么”“实际看见什么”，点开原片复核。 |
| L2 检索块 | 以约 30 秒为起点，优先在相邻句末或镜头切换处划界，建议范围 20–40 秒。长静态镜头按时长切，首尾短块保留。块内分轨存文本和证据 ID；跨界证据使用同一 ID 关联相邻块。 | 用一句台词或动作描述定位到一小段，再回到证据的精确时间。 |
| L3 场景摘要 | 按连续块及场景变化聚合，长场景初始以约 3–5 分钟为一次摘要范围。复用生成模型读取已有证据文本，每条摘要要点引用块及证据 ID。场景目录按起点排序。 | 先了解一个段落讲了什么、发生了什么，再展开证据。 |

上传分片以**字节数**计，服务于断点续传。检索块以**原片时间**计，服务于内容定位。主文件只保存一份；视觉提取时按需生成短窗口，保留少量边界上下文，跨窗口重复观察按来源时间归并。动作模型的时间戳属于估计值。

## 向量存储与检索验收

用本地 `Qwen/Qwen3-VL-Embedding-2B` 分别编码每块的语音文字、字幕文字、动作描述和原始视频画面。只为有内容的来源生成向量。V1 规划使用单节点 Qdrant 和独立的影片集合。按编码模型版本、维度和距离度量区分集合，起测用 2048 维 float32 和余弦相似度。选本地模型便于直接读取本机片段，其运行开销需在目标机器上实测。[模型卡](https://huggingface.co/Qwen/Qwen3-VL-Embedding-2B) · [参考项目的 Qdrant 部署](https://github.com/Xiaoc7r/DOVideo-AI/blob/421dcd2e70e5298ff4d719d2ac8cc4f7c063785b/docker-compose.yml)

SQLite 保存证据正文、原片起止时间、块与证据的关系，以及本次构建预期写入的向量引用。Qdrant 的每个点保存一条向量，并携带 video_id、处理版本、chunk_id 和来源类型。查询先限定视频和已发布版本，再按来源找候选块。例如“哪里说了钥匙”查看语音，“哪里把钥匙放下”可分别查看动作描述和画面。命中后用块 ID 回 SQLite 取证据和播放时间。同一块有多种来源命中时只占一个候选名额。

同一块同一来源使用可重复推导的 UUID（含视频、构建版本、块 ID 和来源类型）。Worker 登记预期点 ID 后，向 Qdrant 批量 upsert 并等待写入生效，再核对预期 ID 和集合配置，最后在 SQLite 标记该版索引就绪。中断后按预期清单补写；Qdrant 暂时不可用时保留已完成证据和待建索引状态。重建时使用新版本，完成后切换已发布版本。[Qdrant 写入接口](https://api.qdrant.tech/v-1-18-x/api-reference/points/upsert-points)

**规模估算与选择依据。** 假设一部电影长 120 分钟、固定每 30 秒一块，共 240 块。每块四路都有内容时共 960 条向量，裸向量占 960 × 2048 × 4 字节，即 7.5 MiB；磁盘占用还包括元数据、日志和索引。首版使用 Qdrant 的理由是历史视频累积后仍可用同一接口做持久化和过滤。单视频离线验收先用精确检索（`exact=true`）。以后按真实库规模和并发比较精确检索与 HNSW 近似检索，记录相同过滤条件下的前五候选重合度、P95 检索耗时和实际磁盘占用，再决定线上检索参数。[Qdrant 查询参数](https://qdrant.tech/documentation/search/)

## 上传可靠性和后台任务

参考项目 DOVideo-AI 使用 HTTP 分片上传，后端将分片写入 MinIO、在 Redis 登记分片号，随后合并原片并保存媒体记录。用户另外提交分析时才投递 RocketMQ。新版沿用分片确认与续传思路，上传成功后自动投递构建任务。[参考项目分片与合并](https://github.com/Xiaoc7r/DOVideo-AI/blob/421dcd2e70e5298ff4d719d2ac8cc4f7c063785b/server/src/main/java/com/example/server/service/ChunkUploadService.java) · [分析任务投递](https://github.com/Xiaoc7r/DOVideo-AI/blob/421dcd2e70e5298ff4d719d2ac8cc4f7c063785b/server/src/main/java/com/example/server/service/AnalysisDispatchService.java)

**建议部署基线为单机 Python API 和一个 Worker。** SQLite 保存业务记录和任务进度，Qdrant 保存可重建的向量索引，本地持久化目录保存分片、原片和派生媒体，Kafka 传递构建任务。

1. 创建上传会话，客户端保留会话 ID 和文件指纹。初始分片大小为 5 MiB；服务端按编号、大小和 SHA-256 校验，分片写成功后才回执。同号同内容重传返回原回执，内容冲突则提示重新校验。
2. 完成上传时检查分片齐全、总大小、整片摘要和可解码视频流。原片写入临时文件，验证后原子改名，再以本地事务登记文件就绪、唯一的 Context 任务和待投递标记。重复提交完成请求返回同一任务。合并中断后可用原会话继续完成。
3. 投递程序发送包含 job_id、video_id 和处理版本的 Kafka 消息，成功后更新投递标记。投递失败保留待发任务并重试。Worker 按任务 ID 幂等处理，持久化阶段成果和恢复位置，重启后续跑；重复消息不会发布两份 Context。记录模型请求次数，网络超时可能产生额外调用。
4. 任务经过排队、处理中、就绪／部分就绪／失败。三轨均已成功完成或已确认无内容，且块、向量和摘要写入成功时标记就绪。无声或无字幕属于正常结果。有可用证据但仍有提取错误时标记部分就绪，全部提取失败时标记失败。修复并重试后重新生成依赖失败阶段的块和摘要。

## 业务表草案

首版以 SQLite 实现这六张逻辑表。完整原片和大体积派生产物存文件，数据库记录可定位的路径及版本。

| 表 | 主要字段与约束 |
|---|---|
| videos | 视频 ID、上传会话、文件名、大小、整片摘要、时长、原片路径、上传状态。一次上传会话对应一条视频。 |
| upload_parts | 视频 ID、分片号、大小、摘要、持久化位置。视频 ID 与分片号联合唯一。 |
| context_jobs | 任务 ID、视频 ID、处理版本、投递状态、处理状态、三轨状态、阶段进度、恢复位置、错误原因、更新时间。视频 ID 与处理版本联合唯一。 |
| evidence | 证据 ID、任务 ID、轨道及来源子类、原片起止毫秒、文字、原片或代表帧引用、提取模型／方法。 |
| retrieval_chunks | 块 ID、任务 ID、原片区间、分轨文本、证据 ID 列表、预期的 Qdrant 集合与分来源点 ID。记录模型版本、维度和索引状态。 |
| scene_summaries | 场景 ID、任务 ID、原片区间、顺序、块 ID 列表、摘要要点及其证据引用。 |

## 首版验收

| 样例 | 可观察的通过条件 |
|---|---|
| 单文件上传与恢复 | 页面一次接受一份视频。上传中断并刷新后只补缺片；重复提交完成操作、服务重启后，得到同一视频和同一构建任务。 |
| 消息暂不可用或重复送达 | Kafka 恢复后待发任务能开始；重复消息、Worker 中途重启后只有一个已发布版本，已持久化的阶段成果能复用。 |
| 无声、无字幕、动作清楚 | 前两轨显示无内容，视觉轨生成可回看的动作。用人工标注的“拿起／放下钥匙”片段分别核对动作方向和时间。 |
| 台词与字幕不同 | 在同一段原片中说“钥匙给你”、字幕写“把钥匙收好”、画面出现放钥匙动作。三种记录保留各自来源，点击均落在相应片段。另用只有烧录字幕的样例验 OCR。 |
| 长片与跨界动作 | 至少一份长片覆盖从片头到片尾，末块与原片时长一致。刻意让一个动作跨块，两边引用同一证据，播放可看到完整动作。抽查场景→块→证据均能追溯。 |
| 某一路出错 | 模拟视觉服务超时，页面区分失败与无动作，语音、字幕结果仍可查看；重试能补齐视觉结果。 |
| 向量索引中断与隔离 | 在向量写入途中重启 Worker，再投递相同任务，最终点 ID 与预期清单一致。用两份先后上传的样片分别检查结果，只命中当前视频、指定来源和已发布版本，所有命中块均可回到原片。 |
| 为下一版查询准备数据 | 对人工标好时间的“哪段说了某句话”“哪段字幕出现某词”“哪里发生某动作”各做离线检索。记录正确区间是否进入前五、证据来源是否正确、跳转偏差。另记录每小时视频的处理耗时、模型调用量与费用，用于决定正式切块和采样参数。 |

## 开发顺序与待定指标

1. 上传与恢复。用同一原片中断并恢复一次上传，重启 Worker 一次，核对原片校验值与任务数。
2. 单片段试通。先用 15 秒短片人工记下台词和动作，分别跑语音、字幕、视觉提取并跳回原片。再用同段无声版单测动作轨。模型接口、Python 示例和时间偏移算法见[模型调用指南](./python-video-context-model-quickstart.md)。
3. 整片构建。在短片证据可用、首批调用费用可接受后再跑整片。记录上传完成到 Context 就绪的时间、各轨处理时长、云模型实际用量、失败重试数；至少抽查片头、中段、片尾的证据链。
4. 离线验证检索。在同一部电影和同一批人工标注问题上比较「只搜文本」与「文本和画面各自召回」。问题覆盖原句、无对白动作以及先说话后发生动作。记录正确事件进入前五的比例。后续上线复核时，再分别报告用户从提问到返回可播放结果的 P50/P95、首条命中率、起止均落在人工标注 ±1 秒内的比例以及每问送去复核的原片秒数。产品负责人根据实测确定时长上限、费用预算和质量门槛。
