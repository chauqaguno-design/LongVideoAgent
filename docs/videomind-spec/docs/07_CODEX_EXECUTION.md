# Codex 开发执行手册

目标是让Codex根据规范持续推进到可验收应用。入口提示词放在prompts/START_HERE.txt；中断后用CONTINUE.txt；独立审查用REVIEW.txt。这里的命令分为本规范包已提供的文档验证命令与Codex实施时需要创建的应用验收命令，两者明确分开。

## 1 把文件放到哪里

已有VideoMind仓库时，将整个规范包放入仓库的docs/videomind-spec目录，保留它内部的相对路径。不要直接用本包AGENTS.md覆盖仓库原有AGENTS；阅读后将必要原则增量合并到合适作用域。现有.specify目录同样先比较，再决定合并，避免破坏已有功能规格。

Codex的工作目录应是目标仓库根目录，启动提示词中的SPEC_ROOT应指向本包目录。没有现成仓库时，先按照baseline审计核实参考仓库和创建隔离checkout；不能把文档包目录误认为已经具备后端项目。

## 2 第一次运行

先读取仓库AGENTS、README、依赖与测试设置，运行git status并记录HEAD。检查已有功能和文件路径与docs/03_ARCHITECTURE.md的差异。建立docs/development/baseline-report.md，列出原本能跑的测试、缺少的服务、已配置能力和无法验证的环节。

然后执行M0任务。基线失败不应被掩盖：区分原有失败、本次引入失败和外部依赖缺失。已有改动不覆盖，测试数据库与生产数据分离。

## 3 每个任务的执行循环

1. 选择依赖已满足的最小task，读取其关联REQ、AT、feature spec与plan。
2. 找出实际代码路径，写出本次改动边界和验证方式。
3. 若有合同冲突，先同步相关spec/contracts/ADR；保持用户原始目标。
4. 实现领域逻辑和adapter，并写有业务意义的正反例测试。
5. 执行任务验收。对渲染任务必须得到真实可解码视频；对线上模型验收必须记录真实请求的模型版本与脱敏usage。
6. 检查diff，避免混入无关格式化、依赖大升级和架构替换。
7. 更新task、AT、PROGRESS与证据路径，再选择下一任务。

不要一次要求模型重写全部平台，也不要仅生成空类、TODO和mock返回后结束。已经授权的普通实现与修复持续推进；不越过环境权限、外部发布和破坏性操作边界。

## 4 执行阶段

| 阶段 | 最重要的演示 | 阻塞时可继续的工作 |
|---|---|---|
| M0 | 现有仓库能启动，合同能校验 | 模型凭证缺失仍可做schema、鉴权和离线媒体测试 |
| M1 | 指定两段源时间，真实拼接，修改后再导出 | 无Flash不影响显式区间编辑和渲染 |
| M2 | 两小时素材按块处理，可展示后半段覆盖和产物 | 无图像embedding可完成ASR/OCR、采样与接口，不假装图搜通过 |
| M3 | 文本和截图命中原片，答案引用证据 | 某一路不可用时标记能力降级，保留可用检索路线 |
| M4 | 自然语言选片形成可修改预览 | 不满足总时长或证据不足时返回明确约束冲突 |
| M5 | 多角色并发、worker重启后恢复且无重复时间线修改 | 单Agent路径持续可用，团队不可用不破坏已有编辑 |
| M6 | 部署、恢复、隔离、故障和盲测证据齐全 | 缺真实验收就标记发布未完成，不修改定义绕过 |

## 5 命令约定

本包现有可执行检查：

```bash
python scripts/validate_spec_pack.py
```

需要Python 3.11或更高，以及requirements-docs.txt中的轻量校验依赖。该命令验证文档引用、需求任务追踪、schema、API引用和示例；不验证业务应用。

目标应用应由M0/M1建立稳定命令入口，优先复用仓库既有工具。建议在README记录以下等价操作：单元测试、数据库集成测试、媒体smoke、provider真实合同测试、端到端流程、质量基准和发布检查。若采用pytest，可将如下路径作为实施要求，创建后再执行：

```bash
python -m pytest tests/unit
python -m pytest tests/integration
python -m pytest tests/media
python -m pytest tests/provider_live -m live
python -m pytest tests/e2e
```

这些tests目录是待建立的目标，不声称参考仓库已有。前端按实际package manager执行lint、类型检查和E2E，锁文件存在时不得切换管理器。Windows上使用实际可用的Python与包管理入口；shell脚本提供PowerShell等价方式或Python跨平台入口。

## 6 模型接入策略

通用模型设置为deepseek-flash。启动时分别验证文本、图片、原生工具调用和结构化JSON协议。配置alias和响应中实际model标识都记录，不将alias当永久不变版本。用户密钥仅从环境注入；缺密钥不请求用户把密钥贴进聊天。

第一条可运行链优先选稳定的工具协议；原生tool calls与已有结构化TOOL_REQUEST路径必须各自通过合同测试。工具响应保留调用ID和关联顺序；provider要求回传的字段交由adapter处理，不在业务日志公开模型内部推理内容。模型无法解析返回时最多进行有界修复；超过上限返回结构化错误并记录证据。

## 7 Codex可以并行的工作

在合同固定后，前端页面、媒体adapter、检索adapter和验收fixture可以并行。数据库迁移、公共schema和时间线写入协议指定单一负责人，避免多Agent各自定义字段。每个开发子Agent拥有明确文件范围；合并前统一运行合同与集成检查。

开发时的Codex子Agent与产品中的Agent Team是不同概念。即使开发过程并行，产品仍必须实现自己的TaskBoard、Mailbox和恢复机制；不能把开发工具的能力当成产品已具备能力。

## 8 如何处理需求变更

需求变更记录旧行为、新行为、原因、受影响REQ、合同迁移和回归AT。先更新规范，再实施；历史验收记录保留。若只是参数调优，冻结开发集与盲测集边界，并记录配置版本；不得使用盲测失败数据反复调到过关后仍称其为盲测。

## 9 最终交付要求

交付可运行代码、依赖锁、数据库迁移、无密钥的env示例、服务编排、真实视频demo、模型集成报告、基准报告、恢复演练、操作文档和已知限制。最终答复必须列出哪些功能通过真实链路验证、哪些仅离线验证、哪些被阻塞。不能把本包的规范完成状态替换成应用完成状态。
